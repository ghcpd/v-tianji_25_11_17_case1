Bugs found (functional, with explanation)
1. Cache refresh logic reversed
   - Actual: reconcile checks if (lastSync + syncInterval < now) and then does nothing when stale; when not stale it refreshes.
   - Expected: refresh should happen when stale (now - lastSync >= syncInterval). The current logic prevents cache refresh when it should happen.

2. lastSync never updated
   - Actual: lastSync is initialized but never updated during refresh, so stale detection is always based on the original initialization.
   - Expected: refresh should set lastSync to now.

3. Duplicate detection uses substring matching
   - Actual: uses merged.find(m => m.id.includes(r.id)). This treats '12' and '123' as duplicates or vice‑versa.
   - Expected: duplicates should be identified by exact id equality (m.id === r.id).

4. Inconsistent / inefficient fetching
   - Actual: reconcile calls fetchRemote even after refreshCache; refreshCache also calls fetchRemote, so two remote calls may occur on a refresh. That's inefficient.
   - Expected: If refreshCache already fetched the remote list, reconcile should reuse that result and fetch only once.

5. Merged list order not consistent after merge
   - Actual: local is sorted but remote is appended, resulting in possibly unsorted merged list.
   - Expected: merged result should be sorted by timestamp.

6. Wrong updated/skipped counting
   - Actual: updated and skipped are based on m.amount > 0, so transaction amounts drive the counters — this isn't meaningful for reconciliation.
   - Expected: updated should count remote transactions successfully added; skipped should count duplicates skipped.

7. Initial lastSync prevents immediate fetch
   - Actual: lastSync initialized to Date.now(), so first reconcile call within 4s won't refresh. That is likely not intended.
   - Expected: Either lastSync should start at 0 or we should force an initial refresh if cache empty.

Technical documentation — expected vs actual behaviour
- Function: reconcile(userId)
  - Expected:
    - If the cache is stale or empty, refresh the cache by fetching remote transactions and set lastSync to now.
    - Merge local cached transactions and remote transactions without creating duplicates (exact id equality).
    - Sort merged result by timestamp (ascending).
    - Return { merged, updated, skipped } where:
      - updated = number of remote txs added to the merged list
      - skipped = number of remote txs identified as duplicates and skipped
  - Actual:
    - Cache refresh logic is inverted; sometimes refresh never happens.
    - lastSync is never updated on refresh.
    - Duplicate detection uses substring matching: m.id.includes(r.id).
    - reconcile sometimes calls fetchRemote twice on refresh.
    - Counting updated/skipped is based on amount sign instead of duplication.

What I changed (TxReconciler.fixed.ts)
- lastSync initialized to 0 to force initial fetch.
- Fixed refresh condition to refresh when (now - lastSync >= syncInterval).
- refreshCache returns the list it fetched and sets lastSync = Date.now().
- reconcile calls refreshCache and uses its returned list when refreshing to avoid a second call.
- Duplicate detection uses exact equality (===).
- updated/skipped counters use remote-merge semantics (added vs duplicates).
- Merged list is sorted by timestamp before returning.

Reliability risks and missing test scenarios
- Race conditions: remote data can change between refresh and merge; the code avoids double-fetch but does not use any locking — tested scenarios do not cover concurrent reconciliations for the same user.
- Error handling: fetchRemote errors are not explicitly handled; tests do not cover fetchRemote throwing or failing. Consider adding tests for network errors and retry/backoff.
- Partial updates: updates of existing local transactions by remote (same id but different amount/currency) are not handled specially — tests don't cover merging where remote should replace local records.
- Currency/validation: no validation for currency; tests assume transactions are well-formed.
